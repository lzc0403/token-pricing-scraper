site.py 单文件 2870 行巨型单体，CSS/JS/HTML/Python 混杂
core/site.py
▶
问题定位
core/site.py 包含 2870 行代码，其中：嵌入式 CSS 约 400 行（设计令牌、响应式断点、组件样式）、嵌入式 JavaScript 约 500 行（汇率交互、排序、Excel 导出、侧边栏）、Python 渲染逻辑约 1970 行（20+ 渲染函数、数据构建、站点组装）。所有前端代码以 Python 三引号字符串内嵌，无独立 .css/.js 文件。
根因分析
项目从简单脚本演进而来，站点生成初期将前端资源内嵌可减少文件管理开销。但随着功能增长（峰谷定价、主流目录卡片、3D 倾斜效果、Excel 导出、portal 链接卡片），site.py 膨胀至接近 3000 行。核心问题：关注点未分离——数据构建、HTML 模板、CSS 样式、JS 交互四层逻辑混杂在同一文件中，任何前端调整都需要修改 Python 文件，增加回归风险。IDE 对内嵌字符串中的 CSS/JS 无语法高亮和补全，维护效率低下。
🔧 修复建议
渐进式拆分（不破坏现有 CI 流程）：
1. 短期：将 CSS 提取到 site/assets/style.css，JS 提取到 site/assets/app.js，site.py 仅负责生成 HTML 并引用外部资源。用 {{CSS_CONTENT}} 占位符→<link> 替换。
2. 中期：将 site.py 按职责拆分：site_builder.py（数据组装）、site_renderer.py（HTML 模板）、site_assets.py（资源管理）。
3. 长期：引入 Jinja2 模板引擎替代字符串拼接，实现模板与逻辑彻底分离。
注意：拆分时必须保持 JS 依赖的类名（js-cny-main/js-rmb-hint/js-row 等）不变，这是 MEMORY.md 明确的铁律。
2
OpenAI GPT-5.6 长上下文价格硬编码，脱离页面数据源
scrapers/openai.py
▶
问题定位
scrapers/openai.py 中 _LONG_CONTEXT_PRICES 字典硬编码了 GPT-5.6 Sol/Terra/Luna 的长上下文价格（如 256K+ token 档位），这些价格不从 developers.openai.com 页面抓取，而是手动维护。当 OpenAI 调整长上下文定价时，此字典不会自动更新，导致站点展示过期价格。
根因分析
OpenAI 定价页使用 Astro 预渲染，TextTokenPricingTables 组件的 JSON 结构中长上下文档位可能以不同组件/布局呈现，当前 _parse_rows_value 的嵌套数组解析逻辑无法覆盖。开发时选择了硬编码作为权宜之计，但未设置后续清理计划。核心风险：硬编码价格与页面真实价格产生偏差时，用户获得错误信息，违背项目「价格透明」的核心价值。
🔧 修复建议
1. 短期：在 _LONG_CONTEXT_PRICES 上方加 # TODO: 确认页面结构后改为动态抓取 注释 + 在 audit.py 的 RATE_MISMATCH 检查中对比硬编码价与 OpenRouter 同模型价，偏差超阈值时告警。
2. 中期：分析 OpenAI 定价页 DOM 结构，扩展 _parse_rows_value 支持长上下文档位解析，删除硬编码字典。
3. 兜底：在 OpenRouter verify 层增加 OpenAI 长上下文价格交叉校验，若 OpenRouter 有对应模型则作为基准。
中 / MEDIUM 6 项 — 建议在迭代中逐步解决

百炼缓存命中价按输入 × 20% 假设计算，非页面真实值
scrapers/bailian.py
▶
问题定位
scrapers/bailian.py 第 10 行 CACHE_HIT_RATIO = 0.2，缓存命中价 = 输入单价 × 0.2。这个比率是假设值，不来自百炼 API 返回数据。如果阿里云调整缓存折扣策略（如改为 10% 或 30%），此值不会自动更新。
根因分析
百炼 JSON 文档 API（help.aliyun.com/help/json/document_detail.json）返回的定价结构中可能不包含独立的缓存命中价格字段（仅有输入/输出），开发者基于行业惯例（缓存命中通常为输入价的 10%-25%）选择了 20%。风险：与其他数据源（如腾讯云明确标注缓存命中价）对比时，百炼的缓存价可能系统性偏高/偏低，影响用户比价决策。
🔧 修复建议
1. 在百炼记录的 condition 字段标注「缓存价按输入×20% 估算」，让用户知道这是推算值。
2. 在 audit.py 的 CACHE_GT_INPUT 检查基础上，增加 CACHE_RATIO_ANOMALY 检查：当某源的缓存/输入比率与同模型其他源偏差超 15% 时标记为中严重度。
3. 排查百炼 API 返回体是否真的无缓存价字段，若有则直接取真实值。

17 数据源顺序执行，Playwright 超时 40s × N 拖慢 CI
main.py
▶
问题定位
main.py 的 run() 函数在 for 循环中顺序执行 17 个数据源的 scraper.run()。每个 Playwright 源（aliyun_intl、tencent、tencent_cn、volcengine_intl 等）超时 40s，加上 networkidle 等待和 scroll-to-bottom，单次完整抓取可能耗时 5-8 分钟。GitHub Actions 免费层有 6 分钟 job 超时限制。
根因分析
设计初期数据源少（3-5 个），顺序执行足够快。随着数据源增长到 17 个，且多个需 Playwright SPA 渲染，总耗时线性增长。瓶颈：Playwright 浏览器实例的启动/关闭开销 + 页面等待时间无法通过代码优化显著缩短，只能通过并行化解决。
🔧 修复建议
1. 短期：用 concurrent.futures.ThreadPoolExecutor(max_workers=4) 并行执行非 Playwright 源（requests + JSON API），Playwright 源仍顺序执行（浏览器实例资源竞争）。
2. 中期：Playwright 源使用共享浏览器实例 + 多 context/page，减少启动开销；或改用 asyncio + playwright.async_api。
3. 兜底：CI 超时从 6 分钟调到 10 分钟（GitHub Actions 免费层最大 6 分钟 → 考虑 split job 或 self-hosted runner）。

CSS/JS 内嵌 Python 三引号字符串，IDE 无语法支持
core/site.py
▶
问题定位
site.py 中约 400 行 CSS 和 500 行 JS 以 """...""" 形式内嵌在 Python 文件中。IDE（VSCode）对字符串内的 CSS/JS 无语法高亮、无 IntelliSense、无格式化、无 lint。开发者修改 CSS 属性或 JS 函数时容易出语法错误，且无法使用前端工具链（Prettier、ESLint、Stylelint）。
根因分析
静态站点生成器通常将前端资源作为独立文件管理。本项目选择内嵌可能是为了简化 GitHub Pages 部署（单 HTML 文件即可发布）。但随着 CSS/JS 复杂度增长，内嵌方式的维护成本已超过单文件部署的便利性。
🔧 修复建议
与 Issue 1 同步解决：提取 CSS/JS 到独立文件 → site.py 读取文件内容并内联到 HTML（<style>{{css}}</style>）。这样既保持单 HTML 文件部署，又获得 IDE 语法支持。或直接使用 <link>/<script src> 引用，GitHub Pages 支持多文件部署。

抓取数据无前置输入校验，恶意/异常数据直接进流水线
scrapers/base.py
▶
问题定位
scrapers/base.py 的 fetch_url() 返回 HTML 后直接交给 parse() 解析，无 HTML 结构校验。各 scraper 的 _rec() 工厂生成的 record 字典无 schema 校验就写入 prices.json。audit.py 的 Tier1 检查在数据生成之后才执行（gate 模式），如果数据源返回恶意内容（如 XSS payload 注入到模型名），可能被写入 JSON 并最终渲染到 HTML 站点。
根因分析
数据源均为知名厂商定价页，被投毒概率低。但从安全工程角度，不应信任任何外部输入。当前 clean_price() 只处理数字提取，model 字段直接取文本不做 HTML 转义。如果厂商定价页被篡改或 CDN 缓存被污染，恶意内容可能流入。
🔧 修复建议
1. 在 base.py._rec() 或 run() 出口增加字段校验：model 字段 bleach.clean(model, tags=[]) 去除 HTML 标签；input_price/output_price 强制 float 转换 + 非负校验。
2. 在 site.py 的 _table_row() 渲染模型名时使用 html.escape()（当前可能已有，需确认）。
3. 在 audit.py 增加 SUSPICIOUS_MODEL_NAME 检查：模型名含 </>/script 时标记为 high。

tests/
▶
问题定位
tests/ 目录有 5 个测试文件，覆盖：audit_gate（门控逻辑）、parsers（全 scraper fixture 测试）、mainstream_catalog（目录校验）、site_mainstream（站点数据生成）、mainstream_ui（未读但存在）。但 core/openrouter_verify.py（251 行，含价格交叉校验逻辑）、core/report.py（126 行，报告生成）、core/currency.py（64 行，货币换算）均无独立测试。core/store.py 的 compare_previous delta 检测也无测试。

项目测试策略聚焦于 scraper 正确性（fixture-based 回归测试）和审计门控，对核心工具模块的单元测试投入不足。currency.py 的 enrich() 函数修改 record 字典 in-place，逻辑虽简单但涉及 peak_*_rmb 字段映射，边界情况（None 输入、未知币种）值得测试。openrouter_verify.py 的价格交叉校验逻辑复杂（per-token → per-million 转换 + tolerance 比较），无测试意味着回归风险高。

2. 新建 tests/test_openrouter_verify.py：用 mock raw JSON 测试 OR_PRICE_MISMATCH/OR_ID_MISSING/OR_WHITELIST_MISS 各场景。
3. 新建 tests/test_store.py：测试 compare_previous 的 delta 检测（新增/删除/价格变动）。
4. 目标：核心模块测试覆盖率从 ~60% 提升至 85%+。

AtlasCloud 缓存 fetched_at 为空字符串
scrapers/atlascloud.py
▶
问题定位
scrapers/atlascloud.py 在缓存原始 JSON 时，wrapper 为 {"fetched_at": "", "url": ..., "body": ...}，fetched_at 为空字符串。而 scrapers/openrouter.py 的缓存 wrapper 使用 datetime.now().isoformat()。openrouter_verify.py 读取缓存时对 fetched_at 无特殊处理，但未来若需要按时间排序缓存或判断过期，空字符串会导致解析异常。

🔧 修复建议
在 atlascloud.py 的缓存写入处加 from datetime import datetime + "fetched_at": datetime.now().isoformat()。一行修复。

10
正则归一化静默失败，模型名不匹配时无告警
多个 scrapers
▶
问题定位
scrapers/volcengine_intl.py 的 _normalize() 使用 _SUFFIX_RE/_GA_SUFFIX_RE/_VERSION_DASH_RE 多个正则剥离后缀；scrapers/tencent_cn.py 的 _base_name() 剥离正式版/原厂直供/HighSpeed 等标注；scrapers/bigmodel.py 的 _SUFFIX_RE 剥离新品/预览/Beta。如果正则不匹配（厂商改了命名规则），re.sub 静默返回原字符串，模型名无法归一到 canonical，watchlist 匹配失败 → 该模型从结果中消失。
根因分析
正则归一化是「尽力而为」策略，不匹配不报错是合理设计（避免误杀）。但缺少「匹配失败监控」：当某 scraper 返回的模型名与 watchlist 的匹配率骤降时，应该告警。当前 audit.py 无此检查。
🔧 修复建议
1. 在 audit.py 增加 MATCH_RATE_DROP 检查：对比上次 watchlist.json 的匹配率，如果下降超 20% 标记为 high。
2. 在各 scraper 的 _normalize() 加 logger.debug(f"normalized: {raw} → {norm}")，便于排查。
3. 在 scrapers/base.py 的 run() 返回时记录 {"source": ..., "raw_count": N, "matched_count": M}，低匹配率（<50%）触发 Tier2 检查。

魔术数字散落代码中，缺乏常量化
base.py 等
▶
问题定位
scrapers/base.py 的 Playwright wait_for_function("body.innerText.length > 800") 中 800 是魔术数字；scrapers/bailian.py 的 CACHE_HIT_RATIO = 0.2 已常量化（好）；core/audit.py 的 OUTLIER_PRICE 阈值、CACHE_GT_INPUT 的 60% 阈值部分硬编码在条件判断中。

12
错误处理模式不一致，部分吞异常
多个 scrapers
▶
问题定位
scrapers/base.py 的 fetch_url() 在 requests 失败时 fallback 到 Playwright，Playwright 也失败时返回 None；各 scraper 的 parse() 在 html is None 时返回 []。但 scrapers/openai.py 的 _parse_rows_value() 遇到非预期嵌套结构时可能抛 IndexError，无 try-except 包裹。scrapers/deepseek.py 的状态机解析在非预期行格式时 continue 跳过，无日志。
根因分析
各 scraper 作者风格不同，无统一的错误处理规范。有的倾向 fail-fast（raise），有的倾向 fail-safe（return []），有的静默跳过（continue）。无 logging 框架，错误信息只 print 或被吞。
🔧 修复建议
1. 引入 logging 模块，在 main.py 配置 logging.basicConfig(level=INFO, format="%(asctime)s [%(name)s] %(levelname)s: %(message)s")。
2. 统一错误处理策略：网络错误 → return [] + log.warning；解析错误 → log.error + raise（让 audit Tier2 捕获 SRC_UNREACHABLE）。
3. 在 base.py 的 run() 中 try-except 包裹 parse()，异常时记录到 self.error 字段，供 report.py 展示。
